Courier The API client that lives in your Azure.

A desktop Postman alternative. Your team shares collections through its own Azure Storage containers, secrets stay in Azure Key Vault, and you sign in with your Azure identity. There are no Courier servers, accounts, storage keys or SAS tokens.

Download View on GitHub

Free for macOS, Windows and Linux. Installers are not code-signed yet: how to open them.

Screenshots are captured by the end-to-end test run; the accounts and endpoints are test fixtures.

Why Courier

Your data stays where you already keep it

  • Personal stays on your machine

    Personal collections and environments live only in the app's data on this machine. They are never uploaded and work offline, without signing in.

  • A team is a storage container

    Each team is an Azure Storage container. Azure RBAC on that container is the boundary. Sync uses ETags, and a conflict dialog lets you keep yours, take theirs or keep both.

  • Secrets are Key Vault references

    {{vault:name}} resolves at send time with your identity. Values stay in memory, are never written to disk, and show as •••• in history, the console and code snippets.

  • Your Azure identity, no Courier account

    Sign in in the browser, reuse your Azure CLI login, or use a managed identity on Azure-hosted machines. Courier has no cloud service of its own.

How it works

Three Azure services you already run, and nothing else

Entra ID signs you in, a storage container per team holds the shared collections, and Key Vault holds the secrets, read at send time. Personal items, current values, cookies, history and tokens stay on your machine.

Features

Everything you send from an API client, and a bit more

Requests, auth and scripts

Params, headers, every common body type, and pre-request and post-response scripts with a pm.* subset, sandboxed in QuickJS.

  • Auth: Basic, Bearer, API key, JWT bearer, Digest, OAuth 2.0 (client credentials, and authorization code with PKCE), AWS Signature v4, NTLM, and an Azure identity token, inherited from folders and collections
  • pm.execution.setNextRequest, pm.cookies and pm.visualizer
  • Import Postman v2.0/v2.1, OpenAPI 3 and cURL; export to Postman or Courier JSON
  • Code snippets for cURL, JavaScript fetch and Python requests, with secrets masked

WebSocket and gRPC

Both are saved in collections and synced like HTTP requests, with the same variables, Key Vault references and inherited auth.

  • WebSocket: text and binary messages, saved messages, subprotocols, and a searchable message log
  • gRPC: server reflection or .proto files, all four call types, metadata, deadlines and TLS
  • Key Vault values and tokens appear as •••• everywhere the window shows them

Team sync and conflicts

Join any number of teams with an account URL and a container. Saving marks an item as changed; Sync uploads yours and downloads theirs, team by team.

  • When both sides changed an item, compare the versions and keep mine, take theirs or keep both
  • One team failing never stops the others; a 403 names the role to ask for
  • Before anything goes to a team, Courier scans it for literal credentials

Azure Key Vault, built in

Use {{vault:alias/secret-name}} in the URL, params, headers, body and auth fields. A team can list its vaults once for everyone.

  • A team vault is only used after you approved its host on your machine
  • Scripts read Key Vault only in collections you allow on your machine, and the permission turns off when the scripts change through a sync
  • The Key Vault browser lists secret names, reveals a value for 20 seconds and creates new versions

Collection runner and courier run

Run a collection with iterations, a delay, stop-on-failure and a CSV or JSON data file. The same engine runs headless on build agents.

  • Console, JSON and JUnit reports; exit code 0, 1 on failures, 2 on configuration errors
  • Courier or Postman collection files, or a team collection downloaded read-only
  • Managed identity or Azure CLI sign-in, only when a run needs it

Mock servers, on your machine

Save responses as examples, then serve them from a local mock server per collection, or headless with courier mock.

  • Listens on 127.0.0.1 only and checks the Host header
  • Matches method and path, then the x-mock-response-id, -name and -code headers and query parameters
  • Key Vault references are never resolved by the mock server

Monitors

Scheduled runs of a collection while the app is open: every N minutes or hours, daily, or on weekdays, in local time.

  • An OS notification on failure and once on recovery
  • The last 100 runs per monitor, with secrets masked
  • Unattended runs without the app: courier run from cron or a scheduled pipeline

Command line and container

Run collections in your pipeline

The command-line runner uses the app's engine: the same executor, script sandbox, auth types and Key Vault resolution. It never reads or writes the desktop app's data.

Container image

No Node.js needed. Images for linux/amd64 and linux/arm64 on the GitHub Container Registry.

docker run --rm -v "$PWD:/work" \
  ghcr.io/cguldogan/courier \
  run /work/collection.json

Add --user "$(id -u):$(id -g)" when reports are written into the mounted directory.

From a checkout, with Node.js 22

The runner is one bundle, out/cli/courier.cjs.

npm ci
npm run build:cli
node out/cli/courier.cjs run api.postman_collection.json \
  -e staging.postman_environment.json -r console,junit \
  --reporter-junit-export junit.xml
  • Exit codes 0 when everything passed, 1 when a test or request failed, 2 for usage or configuration errors.
  • Azure sign-in in a container works with a managed identity, including AKS workload identity (AZURE_CLIENT_ID, AZURE_TENANT_ID, AZURE_FEDERATED_TOKEN_FILE). The Azure CLI is not in the image. Not yet tried against real Azure.
  • Private CAs: mount the certificate and set NODE_EXTRA_CA_CERTS.
  • courier mock listens on 127.0.0.1 only, so in a container it is reachable from inside that container (or with --network host on Linux).

Security model

Built for credentials, honest about its limits

  • Secrets are fetched in the main process at send time, kept in memory for a short time and masked as •••• wherever they could show up outside the live request.
  • Team content is untrusted: team Key Vault hosts and OAuth hosts need approval on each machine, and team scripts cannot read Key Vault unless you allow it for that collection.
  • OAuth tokens are encrypted with the OS keystore or kept in memory only, and never synced.
  • The renderer is sandboxed under a strict Content Security Policy; HTML previews and visualizer templates run no scripts and load nothing from the network.

Known limits

  • Installers are not code-signed or notarized yet.
  • Courier has been tested against the Azurite emulator and a mock Key Vault. Behaviour against real Azure role assignments has had little testing.
  • A request in a team collection is sent to whatever host it names. Review collections from others before sending them.

Opening an unsigned build

The installers are not signed with a developer certificate, so your system warns on first launch. There is no auto-update: install a new version over the old one.

macOS
Ad-hoc signed and not notarized. After the warning, open System Settings → Privacy & Security, choose Open Anyway next to the message about Courier, and confirm. Or, after copying the app to Applications: xattr -dr com.apple.quarantine /Applications/Courier.app
Windows
SmartScreen shows “Windows protected your PC”. Choose More info → Run anyway.
Linux
chmod +x Courier-*.AppImage before running it, or sudo apt install ./Courier-<version>-linux-<arch>.deb.
Verify
shasum -a 256 -c SHA256SUMS --ignore-missing (macOS) or sha256sum -c SHA256SUMS --ignore-missing (Linux).
